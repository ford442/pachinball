### B. GitHub issue — draft (separate Claude session; no file overlap with §A)

```markdown
Title: #503 A3 + A4 — one throw must not freeze the game, and apiFetch must not drop Accept or post a score twice

## Context
Part of #503 (P0 production hardening, Noah's 11-04 audit of `25f12802`). Today's swarm is fixing CI and toolchain (workflows, build-wasm.sh, degrade spec). This issue covers two runtime defects that no gate catches, in files the swarm does not touch:

1. **No fault isolation.** `FrameScheduler.tick` (`src/core/frame-scheduler.ts:160-180`) calls `entry.system.update(dt)` with no try/catch. Babylon's render loop only requeues after `_processFrame` returns, so one throw in any registered system stops rendering for good, and production strips `console.*`, so nobody sees it. `EventBus.emit` (`src/core/event-bus.ts`) has the same problem with handlers, including the batched per-step contact emit (#488 §5).
2. **`apiFetch` (`src/config/api.ts:~79-119`).** `...options` is spread *after* the merged `headers`, so any caller that passes `headers` replaces `Accept: application/json`. The 3-attempt retry on 5xx / network errors also applies to POST, so score / replay / challenge submissions (`supabase/functions/submit-score`, `submit-replay`, `create-challenge`, `put-save`) can land twice.

## Proposed approach (first pass)
- **Scheduler:** wrap each `update` in try/catch. Count consecutive throws per entry; after K (proposal: 3) mark it `removed`, emit a typed `system:quarantined { phase, name, message }` event, and report through `bootError` (survives the console strip). Systems need a stable `name` for this; add an optional `name` to the registration and make it required in the type later.
- **Sim-phase determinism:** a quarantined `physics` / `sim` phase system changes the ball's path. In a replay / verification run that must **fail the run** (flag on the sim clock or replay runner), not continue silently. In live play: quarantine and continue, and the run becomes unranked.
- **EventBus:** try/catch per handler in `emit` and in the contact-batch emit, with the same K-strike quarantine, and no extra allocation on the happy path (the #488 §5 heap probe must stay flat).
- **apiFetch:** build `init = { ...options, headers: { Accept: 'application/json', ...normalize(options.headers) }, signal }`, handling `Headers` instances and tuple arrays as well as plain objects. Retry only GET/HEAD/PUT/DELETE, or POST only when the caller passes an `idempotencyKey`. In that case send `Idempotency-Key` and make the four Supabase functions honour it (store key → response for 24 h in a new table with RLS + a pgTAP test).

## Acceptance criteria (rough)
- Vitest: a system that throws every frame is quarantined after K frames, and the next phase and the next frame still run. One throw followed by a normal frame is not quarantined.
- Vitest: a throwing EventBus handler doesn't stop the other handlers for that event. The allocation probe is unchanged.
- Replay runner: a quarantine in the physics/sim phase during verification marks the run rejected (test).
- Vitest: `apiFetch` with `headers: { 'Content-Type': … }` still sends `Accept`. `Headers` instances are merged. POST without a key is never retried; POST with a key retries and sends the same key every time.
- If the key route is chosen: pgTAP test that a duplicate key returns the first response and inserts nothing (`supabase test db`).
- `tsc -b`, lint, `check:index-strict`, vitest, `npm run build`, `check:bundle` all green, and `entryGzipKb` within budget.

## Open questions for Noah
1. K for quarantine: 3 consecutive throws, or 1 for sim-phase systems?
2. Idempotency key vs "never retry POST": is the Supabase change worth it now, or after #503 A5 telemetry?
3. Should a live-play quarantine show the player a toast, or only flip the run to unranked?
4. Does the replay-verifier service (`services/replay-verifier/`) need the same "quarantine ⇒ reject" rule, or is the runner flag enough?
```
