# [P1][Audio] Typed, pooled voice worklet generated from src/audio (expands #526)

## Context
`public/audio/pachinko-voice-processor.js` (79 lines) is the only hand-written application JavaScript left in the repo. It's untyped, allocates a voice object for every contact, and drops the oldest voice with `shift()` once 24 are live. `AudioEngine.playVoice()` (`src/audio/audio-engine.ts:152-171`) posts `{type, velocity, impact, metal, spin, fever, pan}`, and the processor re-parses each field with `Number(data.*)`. Pan is already computed on the main thread as `clamp(position.x / 12)` (`audio-engine.ts:160`). The `12` is a magic playfield half-width, and the `playVoice` callers (`src/audio/sound-system-synth.ts:228`, `src/effects/effects-core.ts:336`) don't all pass `position`.
#521 slice 4 (music stems) will start looped stems on the same `AudioContext` and sample clock. This has to land first, or the stems grow a second clock beside a loose script.
This is presentation only: nothing here may read or write sim state, change golden tapes, or touch the physics path.

## Proposed approach (first pass)
1. `src/audio/voice-hit.ts`: a `VoiceHit` interface (`velocity`, `impact`, `metal`, `spin`, `fever`, `pan`, all `number`, pre-clamped) plus `VOICE_POOL_SIZE = 24`, shared by `AudioEngine` and the processor.
2. `src/audio/worklet/pachinko-voice-processor.ts`: the processor in TypeScript. It needs AudioWorkletGlobalScope typings (`AudioWorkletProcessor`, `registerProcessor`, `sampleRate`); either `@types/audioworklet` or a local `worklet-globals.d.ts`, and it must not leak into the DOM lib of the app tsconfig. Add a `tsconfig.worklet.json` referenced from `tsconfig.json`.
3. Fixed pool: 24 voice slots preallocated as struct-of-arrays (`Float32Array`s for phase / envelope / pitch / pan / noise state) at construction. A new hit takes a free slot or **steals the quietest** (lowest current envelope). `process()` and the message handler allocate nothing: no object literals, arrays or closures per hit or per quantum.
4. `scripts/build-audio-worklet.mjs`: esbuild, IIFE, no imports, target ES2022, writes `public/audio/pachinko-voice-processor.js` with a "GENERATED from src/audio/worklet — do not edit" banner. `--check` regenerates in memory and fails on any byte difference. Scripts: `build:worklet`, `check:worklet`; `build` runs `build:worklet` first; CI's check job runs `check:worklet`.
5. Pan from the contact point's playfield x: replace `/ 12` with the active cabinet's playfield half-width (read once per table build, not per hit), and make both callers pass the contact position they already have. If the position isn't available at a call site without touching `src/game/physics/**`, pass it through the existing EventBus payload instead and say so in the PR.
6. Tests (Vitest, Node, globals mocked): load the processor TS with stubbed `AudioWorkletProcessor` / `registerProcessor`; post 500 hits in a burst and run 1000 quanta. Assert the live count stays ≤ 24, the slot arrays are the same identities before and after, and a stolen voice is always the quietest. Assert `getOwnedAudioContextCount() === 1` after `AudioEngine` boot + the worklet load. A drift test runs `check:worklet`.

## Acceptance criteria (rough)
- [ ] No hand-written JS under `public/audio/`; the committed processor is byte-identical to `npm run build:worklet` output, and CI fails otherwise.
- [ ] A 500-hit burst keeps the pool at 24, steals the quietest, and allocates nothing inside `process()` / `onmessage` (structural test).
- [ ] `VoiceHit` is the one message type on both sides; the processor does no `Number()` re-parsing.
- [ ] Pan comes from the contact x scaled by the cabinet's playfield half-width; there's no magic `12`.
- [ ] `AudioEngine` is still the only `AudioContext` (`getOwnedAudioContextCount()`).
- [ ] `tsc -b`, lint, vitest, `npm run build`, `check:bundle` are green; the entry chunk doesn't grow (the processor isn't imported by app code); `verify:replay` is unchanged (no tape touched).

## Open questions for Noah
1. Typings: add `@types/audioworklet` as a devDependency, or keep a hand-written `.d.ts`?
2. Steal policy: quietest voice, or the oldest among the quietest N? Should gold-ball / jackpot voices be immune to stealing?
3. Should the generated `.js` stay committed (needed for `vite dev` without a pre-step), or be emitted by a Vite plugin at build/dev time and gitignored?
4. Is reduced-audio scaling (`* 0.45` velocity, `* 0.35` pan) still main-thread policy, or does it move into the processor as a parameter?
5. Is 24 still the right pool size for mobile, or should it be per tier?
