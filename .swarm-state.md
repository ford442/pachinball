# Slice B — Adventure geometry cutover (#383)

## Objective

Close the collider-shape gap that keeps Adventure mode on Rapier, and prove it
by getting ONE adventure track running in `wasm-owner` with the second Rapier
world unstepped. Issue #383 claims adventure tracks are trimeshes and
heightfields; they are not — across `src/adventure/tracks/*.ts` and
`track-builder.ts` the inventory is cuboid, cylinder and ball, plus a single
`convexHull` in `prism-pathway`. Rotated cuboids were already covered by
`addStaticBox`'s quaternion, so the genuinely missing shapes were exactly two:
static cylinder and static sphere. This slice adds those, replaces every
inline `rapier.ColliderDesc` call in adventure with one declarative descriptor
type consumed by both engines, splits `track-builder.ts`, and gates the Rapier
skip per track. It does NOT delete Rapier.

## Blocked on

Nothing blocking the slice. Three things for Noah:

1. **`playwright smoke` is red, and it is red on `main` too.** The failing
   set is identical: `basic-gameplay`, `verify_prism_core` and
   `mobile-touch-smoke`, all timing out on `locator.click` — the same three
   that fail in `main`'s runs 101, 102 and 104. Nothing in this PR can fix
   it, and it is the only red check. Worth its own issue: it means the
   blocking e2e gate has been red on `main` for at least three runs, so it
   is not currently gating anything.

2. **Pre-existing: every adventure track that still steps Rapier under
   `wasm-owner` traps the Rapier WASM module.** Verified against `main`
   (70d0ee5) in a clean worktree: `PRISM_PATHWAY` throws `recursive use of
   an object detected which would lead to unsafe aliasing in rust`, and so
   does `SYNTHWAVE_SURF`. On this branch synthwave-surf no longer crashes
   because Rapier is no longer stepped for it
   (`{"crashed":false,"rapierMs":0,"unexported":[],"descs":174}`). The other
   13 tracks still hit it. Compounding it, the Rapier ball is disabled in
   this mode (`disableRapierBody`, unchanged from `main`), so adventure
   colliders and portal `intersectionPair` queries could never reach it even
   when Rapier does step. That is a pre-existing defect in the dual-engine
   path, out of scope here, but it means the remaining tracks are
   effectively unplayable in the production default engine and Slice C
   should treat it as the first thing to fix, not a surprise. Consequence
   for this slice: there is deliberately NO browser test for a track the
   gate refuses — the first attempt failed in CI with `Execution context was
   destroyed`, because the page's rAF loop hits the trap and kills the page
   mid-test. The refusal logic lives in tests/wasm-owner-adventure.test.ts.

3. **`tests/wasm-owner-flipper.spec.ts` was flaky; root-caused and fixed.**
   It failed and passed on the *same commit* across the push and
   pull_request runs, and finally failed on 43a6a70 whose entire diff is
   this markdown file — proof it was uncorrelated with code. Root cause: the
   spec placed the ball, pressed Digit1, then stepped physics in a *second*
   page.evaluate. The page's own rAF loop keeps calling stepPhysics across
   those round trips, so on a slow runner the flipper completed its whole
   sweep before the scripted loop began and never struck the ball.

   Demonstrated directly by holding the old shape and inserting a 2 s rAF
   window: `oldWay(vz)=-0.13` — the exact value CI reported — against
   `newWay(vz)=-4.443` for the atomic shape under the same delay. Fresh-start
   measurements were `-12.5` on this branch vs `-12.1` on main, so the branch
   was never the cause.

   Fix: placement, flipper engage and stepping now happen in one evaluate,
   with the flipper driven via `inputActions.handleFlipperLeft` so its sweep
   starts in the same tick as the stepping. It stays engaged because an
   unheld key yields `flipperLeft: null`, which stepPhysics skips. The
   assertion (`|vz| > 0.5`) is unchanged — nothing was weakened, skipped or
   quarantined. The real keyboard path keeps its own coverage in
   tests/keyboard-input.spec.ts. This is a pre-existing spec outside the
   slice; it was touched because CI offers no re-run permission (403) and
   the flake would otherwise have blocked this PR indefinitely. Confirmed
   fixed: both WASM Build + Parity runs on 8e5291d passed, where the same
   job had been failing on roughly half of all prior runs.

## NOT STARTED / DEFERRED

Slice C is untouched. Specifically, none of the following exists or was
attempted:

- Triangle-soup / heightfield / any mesh collider, and no BVH or GJK/EPA.
  (`TriangleMesh.h` / `Heightfield.h` from #383 were deliberately not written —
  no track needs them.)
- Force-field volumes (`ForceField.h`).
- Dynamic OBB crates, box-vs-box, capsule-vs-capsule, cloth, soft bodies.
- `src/adventure/tracks/prism-pathway.ts`'s `convexHull` — still Rapier, now
  explicitly declared via `markUnexportedCollider('prism convexHull')`.
- Cutting over the other 13 tracks. **Adventure still steps Rapier for every
  non-flagship track**; `synthwave-surf` is the only one the gate lets through.
- Removing `@dimforge/rapier3d-compat` or shrinking the 2.15 MB chunk. Rapier
  still serves table flipper meshes, the missing-bundle fallback, and 13
  tracks.
- Hand-written WASM SIMD intrinsics (`-msimd128` auto-vectorisation unchanged).
- Routing adventure conveyor/gravity-well/damping/chroma-gate zones off
  Rapier's `intersectionPair`. synthwave-surf has none of those, so the slice
  did not need it; any track that has them will need it before its own
  cutover. Exit portals likewise keep Rapier stepping while they are up.

   polling queries are what is left.

   two rejections blocking most tracks are non-OBB sensor volumes and
   prescribed-spin (`kinematic-velocity`) bodies; adding a cylinder sensor
   volume and a spin-driven mover to C++ would unblock most of the remaining
   set in one go.
